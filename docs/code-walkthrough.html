1. The story: a document assembly line

Like I'm 10 Imagine a lease is a giant, boring paper full of tricky grown-up words. We build a little factory with three workers in a row. Worker 1 cuts the paper into pieces. Worker 2 puts a red, yellow, or green sticker on each piece. Worker 3 writes what each piece means in easy words. At the end you get a neat pile you can actually understand.
Say it like a pro "It is a three-stage serverless pipeline orchestrated by AWS Step Functions. Each stage is a Python Lambda that calls Claude through Amazon Bedrock. A web page submits a document, then polls for the result, because the work takes longer than API Gateway's 29-second limit."

2. Key words, in plain English

Lambda

Kid: a tiny worker that wakes up only when there is a job, then goes back to sleep.

Pro: serverless function; we pay per run, no servers to manage.

Step Functions

Kid: the foreman with a checklist. Do step 1, then 2, then 3. If someone trips, try again.

Pro: managed workflow service; state machine with Retry and Catch.

DynamoDB

Kid: a giant notebook with one line per job.

Pro: serverless NoSQL key-value store. We use two tables.

Bedrock

Kid: the door to the smart AI helper (Claude).

Pro: AWS service that hosts foundation models. We call converse().

CDK

Kid: instead of building the factory with your hands, you write a recipe and AWS builds it.

Pro: infrastructure as code; Python turns into a CloudFormation template.

API Gateway

Kid: the front desk. It takes requests and sends them to the right worker.

Pro: HTTP API with two routes and rate limits.

Retry / Catch

Kid: if a worker drops the paper, try again up to 3 times. Still failing? Write "failed" and stop.

Pro: error-handling rules in the state machine.

Audit log

Kid: a diary where each worker writes what it did.

Pro: one row per stage per job; also powers the progress bar.

Mock

Kid: a pretend AI for practice, so we do not need the real one.

Pro: a test double; keeps tests free, fast and offline.

JSON

Kid: a tidy way to write a list with labels.

Pro: the structured format every stage returns and validates.

llm.py: asking the AI

backend/src/shared/llm.py
def call_model(system_prompt: str, user_text: str) -> dict:
    client = boto3.client("bedrock-runtime", region_name=REGION)
    response = client.converse(
        modelId=MODEL_ID,
        system=[{"text": system_prompt}],
        messages=[{"role": "user", "content": [{"text": user_text}]}],
        inferenceConfig={"maxTokens": 4000, "temperature": 0},
    )
    reply_text = response["output"]["message"]["content"][0]["text"]
    return json.loads(reply_text)
PartWhat it means
system_promptThe rules we give the AI ("use only this text, do not invent").
user_textThe material to work on (the document or the clauses).
client.converse(...)The real call to Claude. No password or API key in our code. AWS gives the Lambda a role, and the role grants access.
temperature: 0"Be as steady as possible." Same input should give almost the same answer.
json.loads(...)Turns the AI's reply text into a Python dictionary. If the reply is not valid JSON, this raises an error, and the stage fails and retries.
Say it like a pro "All three stages share one thin wrapper over Bedrock's converse API. In tests we replace it with a fake, so tests are free and need no AWS login."

memory.py: the diary (audit log)

backend/src/shared/memory.py
def write_audit(job_id: str, stage: str, summary: dict) -> None:
    table = boto3.resource("dynamodb", region_name=REGION).Table(AUDIT_TABLE)
    table.put_item(Item={
        "job_id": job_id,
        "stage": stage,
        "timestamp": int(time.time()),
        **summary,
    })

It saves one row: which job, which stage, when, and a short summary. **summary means "also add every item from the summary dictionary". The table's key is job_id plus stage, so a retry overwrites the same row instead of adding a duplicate.

4. Stage 1: the clause extractor

Like I'm 10 Worker 1 takes scissors and cuts the long paper into numbered strips. It must not change a single word, and it must not make up new strips.
backend/src/agents/clause_extractor/prompt.md + handler.py

The instructions live in their own file, prompt.md. The handler just reads it: SYSTEM_PROMPT = (Path(__file__).parent / "prompt.md").read_text(). So you can read or change an agent's instructions without touching code.

You split legal documents into clauses.

Rules:
- Use ONLY the text you are given. Do not add, guess, or invent anything.
- Copy each clause's wording exactly. Do not rewrite or summarise it.
- Number the clauses 1, 2, 3, ... in the order they appear.
...
- Reply with valid JSON only, in this shape:
  {"clauses": [{"clause_id": 1, "original_text": "..."}]}

This is the instruction card we hand the AI. It is strict on purpose: "only this text", "copy exactly", and a fixed JSON shape so the next worker can read the answer.

def validate_clauses(reply, document_text):
    clauses = reply.get("clauses") if isinstance(reply, dict) else None
    if not isinstance(clauses, list) or not clauses:
        raise ValueError("reply must contain a non-empty 'clauses' list")

    document = _squash(document_text)
    for clause in clauses:
        if "clause_id" not in clause or "original_text" not in clause:
            raise ValueError("each clause needs 'clause_id' and 'original_text'")
        if _squash(clause["original_text"]) not in document:
            raise ValueError(f"clause {clause['clause_id']} is not found in the document")
    return clauses
PartWhat it means
reply.get("clauses")Take the "clauses" list out of the AI's answer.
not clausesAn empty list is not acceptable. Raise an error.
"clause_id" not in clauseEvery piece needs a number and its text.
_squash(...) not in documentThe anti-invention check. Every clause the AI returns must really exist in the original document (spaces ignored). If the AI made one up, we reject it.
raise ValueError"Stop. This stage failed." Step Functions sees the failure and retries.
def handler(event, context):
    job_id = event["job_id"]
    text = event["text"]

    reply = call_model(SYSTEM_PROMPT, text)         # 1. ask the AI
    clauses = validate_clauses(reply, text)         # 2. check its answer

    write_audit(job_id, STAGE_NAME, {               # 3. record what we did
        "status": "ok",
        "clause_count": len(clauses),
    })
    return {**event, "clauses": clauses}            # 4. pass the result on
  1. handler(event, context) is the front door. AWS calls it. event is the input, here {"job_id": ..., "text": ...}.
  2. Ask the AI. 2. Check the answer. 3. Write a diary line. 4. Return the same data plus the new clauses.
  3. {**event, "clauses": clauses} means "copy everything from event, and add clauses". The next stage receives it.
  4. The audit row is written after validation, so a failed check never logs a success.
Say it like a pro "Stage 1 is a thin orchestration function: call the model, validate the output against the source document to guard against hallucinated clauses, write an audit record, and return the enriched state."

5. Stage 2: the risk flagger

Like I'm 10 Worker 2 reads each strip and puts a sticker on it: green (fine), yellow (look closer), or red (danger!). It also writes why in one short sentence.
backend/src/agents/risk_flagger/handler.py
RISK_LEVELS = ["low", "medium", "high"]
CATEGORIES = ["auto-renewal", "hidden fees", "cancellation", "liability", "other"]

6. Stage 3: the plain-English rewriter

Like I'm 10 Worker 3 explains each strip like a friendly teacher: short sentences, no hard words, same numbers and dates. Then we staple the "this is not legal advice" note on the front ourselves.
backend/src/agents/plain_english_rewriter/handler.py
finished = [{**c, "plain_english": rewrites[c["clause_id"]]} for c in clauses]

write_audit(job_id, STAGE_NAME, {"status": "ok", "clause_count": len(finished)})

result = {"disclaimer": DISCLAIMER, "clauses": finished}
return {**event, "clauses": finished, "result": result}
LineWhat it means
[{**c, "plain_english": ...} for c in clauses]A list comprehension: for every clause, copy it and add its plain-English text. One line instead of a loop.
"disclaimer": DISCLAIMERThe disclaimer comes from our config, not from the AI. A test checks that even if the AI sends its own, we ignore it.
"result"The finished package the web page will show. The final step in Step Functions saves it into DynamoDB.
Honest limit (risk R2) Code cannot prove an explanation is true to its clause. We reduce the risk with a strict prompt, showing the original wording next to every explanation on the page, and the disclaimer. Say this openly to your guide. It shows you understand the limits.

get_status: "is it done yet?"

backend/src/api/get_status/handler.py
job = table.get_item(Key={"job_id": job_id}).get("Item")
if not job:
    return _response(404, {"error": "job not found"})

if status == "SUCCEEDED":
    reply["completed_stages"] = TOTAL_STAGES

  • 404: no such ticket number.

Say it like a pro "The API is asynchronous: POST returns 202 with a job id, and the client polls a status endpoint. Progress is derived from the audit table, so there is no extra state to keep in sync."

9. The recipe: the CDK stack

Like I'm 10 Instead of building the factory by hand, we write one recipe: "two notebooks, five workers, one foreman, one front desk". AWS reads the recipe and builds it. When we are done, one command tears it all down.
backend/infra/: stack.py joins the parts; storage.py, agents.py, orchestrator.py, api.py, website.py build one part each
FileWhat it builds
storage.pyTwo DynamoDB tables, suman-jobs and suman-audit-log. Pay-per-use, and DESTROY means cdk destroy deletes them.
agents.pyFive Python 3.12 Lambdas. Gives the three stages permission for Bedrock (one model only) and the tables they need. Nothing more.
orchestrator.pyThe foreman: extract, flag, rewrite, save. With Retry and Catch.
api.pyThe front desk: POST /jobs and GET /jobs/{job_id}, with CORS and rate limits.
website.pyThe web page: a private S3 bucket behind CloudFront, uploaded on every deploy.

                          retry_on_service_exceptions=False)
step.add_retry(errors=["States.ALL"], max_attempts=3,
               interval=cdk.Duration.seconds(2), backoff_rate=2.0)

...
for step in (extract, flag, rewrite):
    step.add_catch(save_failure, errors=["States.ALL"], result_path="$.error_info")

definition = extract.next(flag).next(rewrite).next(save_success).next(sfn.Succeed(stack, "Job done"))
LineWhat it means
payload_response_only=TrueHand the Lambda's output straight to the next step, with no extra wrapping.
add_retry(... max_attempts=3, backoff_rate=2.0)On any failure, wait 2 seconds and try again, then 4, then 8. Up to 3 retries.
add_catch(save_failure)If it still fails, go to "Save failure" and record FAILED with a friendly message.
extract.next(flag).next(rewrite)...The order of the line. Read it left to right like a sentence.

Safety choices in the recipe

  • Least privilege: only the three stages may call Bedrock, and only that one model. A test checks the permission is not a wildcard.
  • Throttling: 2 requests a second (burst 5), because the API has no login and every request can spend AI money.
  • Prefix: every named resource starts with suman-, so it is easy to find in the company account.
  • Not deployed: python app.py only writes a template on this machine. Nothing is created in AWS until someone runs cdk deploy, and that needs the account confirmation step.

12. Questions your guide might ask

What if the AI makes things up?

Three layers. The prompts say use only the given text. Stage 1 rejects any clause that is not really in the document, and stages 2 and 3 reject answers that skip or add clauses. The AI can never change the original wording, the risk labels, or the disclaimer, because our code owns them. The page also shows the original wording beside every explanation. We say openly that code cannot fully prove an explanation is accurate, so the disclaimer stays.

What happens if a stage fails?

Step Functions retries up to 3 times with growing waits (2, 4, 8 seconds). If it still fails, a catch rule saves the job as FAILED with a friendly message, and the page shows it. Nothing hangs.

Why Step Functions and not Lambdas calling each other?

It gives retries, error handling, and a visible step-by-step history for free. It is also easy to explain: one foreman, three workers.

Why is it asynchronous?

Three AI calls take longer than API Gateway's 29-second limit. So we return a job id immediately and the page polls.

How do you track progress?

Each stage writes one audit row. The status Lambda counts the rows for the job. Two rows means two stages finished.

Is it secure?

It is a demo with no login, so we use only fake documents. Still: no API keys in code (IAM roles), least-privilege permissions (one model only), throttling on the API, and encryption at rest by default. A real product would add authentication and a limit on who can call the API.

What does it cost?

Pennies at demo scale. Lambda, DynamoDB, Step Functions and API Gateway are pay-per-use, and the main cost is the Bedrock calls. cdk destroy removes everything.

Why did you not use SES email?

The spec suggested it, but the page already shows the result, and email setup (sandbox, verified addresses) adds risk for a short build. It is a clean extra to add later.

What would you improve next?

Add login, add a "what to check before signing" list per clause, support file upload through S3, compare results across prompt versions, and add alarms.

Is it deployed?

Yes. One cdk deploy stands up the whole stack, including the state machine and the website (S3 + CloudFront). It is tested locally with 76 tests, and real documents have been run through the deployed pipeline. cdk destroy removes everything.
