1. The project

Q1 Explain the project in simple language.

Short answerDocLens takes a hard legal document, like a lease or insurance policy, splits it into clauses, flags the risky ones, and explains each clause in plain English.

A person pastes or attaches a document on the web page. Three AI helpers then work on it, one after another:

  1. Clause extractor cuts the document into numbered clauses, copying the wording exactly.
  2. Risk flagger marks each clause High risk, Watch out or Minor note, with a reason (for example auto-renewal, hidden fees, cancellation traps).
  3. Plain-English rewriter explains each clause in simple words and adds the "not legal advice" disclaimer.

The page waits, checking every 3 seconds, and then shows the result: a risk bar, and one card per clause with its label, reason, plain English and the original wording.

It runs on AWS: a web page (S3 + CloudFront), an API (API Gateway), five Lambda functions, Step Functions to run the three AI helpers in order, Amazon Bedrock (Claude Sonnet 4.6) for the AI, and DynamoDB to store job status and an audit log.

Q3 What if we do both? Is it big?

Short answerBoth document types (lease, policy, terms) is small. Both user types (ordinary people and lawyers) is big. We chose ordinary people, any document type.

Both document types: the pipeline treats any document as text. The same three agents work for a lease, a policy or terms of service. Only the kinds of traps differ, and the prompts already cover them. Small.

Both user types: lawyers would need exact legal wording, citations and much stricter accuracy, which means far more testing. Too big for 1 to 2 days, and it clashes with the "not legal advice" rule.

Say it like this"One pipeline for any document type, built for ordinary people, so it stays small and easy to test."

Q5 Explain Step Functions for a fresher. How are we going to use it?

Short answerStep Functions is a foreman with a checklist: do step 1, then 2, then 3. If someone trips, try again. If they keep failing, write it down and stop.
WordMeaning
State machineThe whole checklist (ours is suman-doc-explainer-pipeline)
State / stepOne box. Ours: Extract clauses, Flag risks, Rewrite in plain English, Save result, Save failure
Passing dataEach step's output becomes the next step's input
RetryOn failure, wait 2 s and try again, then 4 s, then 8 s (3 retries)
CatchIf it still fails, go to "Save failure": write FAILED so the page shows an error

The journey of one request: start_job saves the job as RUNNING and starts the state machine with {job_id, text}. Each agent runs, checks the AI's answer, writes an audit row, and passes its output on. "Save result" writes SUCCEEDED and the result to the jobs table. Meanwhile the page polls get_status.

Why asynchronous: API Gateway gives up after 29 seconds, and three AI calls take longer. So we return a job id straight away and the page checks back.

def create_pipeline(stack, fns, jobs_table):
    extract = _agent_step(stack, "Extract clauses", fns.extractor)
    flag = _agent_step(stack, "Flag risks", fns.flagger)
    rewrite = _agent_step(stack, "Rewrite in plain English", fns.rewriter)
 
    job_key = {"job_id": tasks.DynamoAttributeValue.from_string(sfn.JsonPath.string_at("$.job_id"))}
 
    # After agent 3: save SUCCEEDED and the result in the jobs table.
    save_success = tasks.DynamoUpdateItem(
        stack, "Save result",
        table=jobs_table,
        key=job_key,
        update_expression="SET #s = :s, result_json = :r",
        expression_attribute_names={"#s": "status"},
        expression_attribute_values={
            ":s": tasks.DynamoAttributeValue.from_string("SUCCEEDED"),
            ":r": tasks.DynamoAttributeValue.from_string(
                sfn.JsonPath.json_to_string(sfn.JsonPath.object_at("$.result"))),
        },
        result_path=sfn.JsonPath.DISCARD,
    )
 
    # If an agent still fails after its retries: save FAILED with a friendly message.
    save_failure = tasks.DynamoUpdateItem(
        stack, "Save failure",
        table=jobs_table,
        key=job_key,
        update_expression="SET #s = :s, #e = :e",
        expression_attribute_names={"#s": "status", "#e": "error"},
        expression_attribute_values={
            ":s": tasks.DynamoAttributeValue.from_string("FAILED"),
            ":e": tasks.DynamoAttributeValue.from_string("The analysis failed. Please try again."),
        },
        result_path=sfn.JsonPath.DISCARD,
    )
    for step in (extract, flag, rewrite):
        step.add_catch(save_failure, errors=["States.ALL"], result_path="$.error_info")
    save_failure.next(sfn.Fail(stack, "Job failed"))
 
    # The happy path, read it left to right.
    definition = extract.next(flag).next(rewrite).next(save_success).next(sfn.Succeed(stack, "Job done"))
 
    pipeline = sfn.StateMachine(
        stack, "Pipeline",
        state_machine_name=f"{PREFIX}-doc-explainer-pipeline",
        definition_body=sfn.DefinitionBody.from_chainable(definition),
        timeout=cdk.Duration.minutes(10),
    )
 
    # start_job needs the pipeline's address and permission to start it.
    fns.start.add_environment("STATE_MACHINE_ARN", pipeline.state_machine_arn)
    pipeline.grant_start_execution(fns.start)

Q6 How did you build the Step Functions part?

Short answerIn Python with CDK, in backend/infra/orchestrator.py. cdk deploy turns it into the real state machine.
  1. One helper per agent step (_agent_step): tasks.LambdaInvoke runs the agent's Lambda; payload_response_only=True passes its output straight on.
  2. Retry: add_retry(errors=["States.ALL"], max_attempts=3, interval=2 s, backoff_rate=2.0). CDK's own hidden retry is turned off (retry_on_service_exceptions=False) so there is exactly one rule.
  3. Save result: a DynamoUpdateItem step writes SUCCEEDED and the result. Step Functions talks to DynamoDB directly; no Lambda needed.
  4. Catch: add_catch(save_failure) on all three agents; Save failure writes FAILED and "The analysis failed. Please try again."
  5. Order: extract.next(flag).next(rewrite).next(save_success).next(Succeed("Job done")). A 10-minute limit for the whole run.
  6. Permission: only start_job may start it (grant_start_execution).

When does a step "fail"? When the agent's code raises an error, for example the AI invented a clause, skipped one, or returned bad JSON.

How it was tested: test_stack.py checks the 3 agent steps, Save result, Save failure, one retry rule each, and a Catch on each. Real lease runs on AWS went through all three steps and ended SUCCEEDED.

def _agent_step(stack, name, fn):
    """One step: run an agent Lambda. Retry up to 3 times if it fails (NFR-4)."""
    step = tasks.LambdaInvoke(
        stack, name,
        lambda_function=fn,
        payload_response_only=True,            # hand the Lambda's output straight to the next step
        retry_on_service_exceptions=False,     # turn off CDK's extra default retry; we use our own below
    )
    step.add_retry(
        errors=["States.ALL"],
        max_attempts=3,
        interval=cdk.Duration.seconds(2),
        backoff_rate=2.0,                      # wait 2 s, then 4 s, then 8 s
    )
    return step
